검증 기준은 원본 `e02eeba66b4801ebae0b686e1b0e4bc03fbf3654`, 사용자가 문제를 보고한 `36d5ddebc37e1a731dadca9912ea39d0992297c8`이다. 수정본은 이 브랜치의 최종 커밋에 포함된 코드이며, 측정 JSON에는 실행 당시 HEAD와 실제 비교 소스의 SHA-256을 함께 기록했다. 이전 ModernV2Verification 결과를 이번 검증으로 재사용하지 않았다.

## 게임 규칙과 기본 수치

일반 현대 지역 시나리오 ID와 지도 데이터 버전은 `modern-regions-v2`/2를 유지한다. **새 게임의 동적 modern state는 3**이다. 현대 메뉴에서 시작하면 시간 기반 건설·생산과 복구한 증가식이 적용된다. 옛 저장의 `state.version=2`는 명시적으로 기존 규칙을 유지한다.

| ------------- | -------------------------: | ------------------------: | -------------------------------------------------------------- |

기지·생산은 소유지, 해안, 기지 종류, 완공·피해·수리 상태, 자금, 가용 인력, 대기 중 생산을 포함한 용량을 core에서 검증한다. 기존 즉시 건설 설정을 명시적으로 켠 경우만 건설·생산 시간이 0이 되며 비용과 인력 검사는 유지한다. 일반 현대 시작은 즉시 건설을 끈다.

육군 편성은 기본적으로 이미 모인 예비 육군을 먼저 사용한다. 부족하면 가용 인력을 새로 동원하며, UI에서 가용 인력을 지정할 수도 있다. 동원 상한에 도달해도 기존 예비 육군을 편성할 수 있다. 예비 인력과 새로 동원한 인력 모두 같은 편성 비용·시간을 적용한다. 새 인력 생산이 아니다.

해군·공군의 자동 생산은 가용 인력과 공통 동원 여유가 있으면 그것을 사용한다. 상한이 가득 찼거나 가용 인력이 부족하면 충분한 **예비** 육군을 승조원·공군 인력으로 이전하여 재훈련한다. 출정·수송·편성에 묶인 육군은 예비 풀에 없어 사용할 수 없다. 명시적으로 가용 인력을 선택한 경우에는 자동 재훈련을 하지 않는다. 예비 raw 병력과 `population.army`를 차감하고 대상 군 인력에 같은 사람 수를 추가하여 N0·전체 군 인력·공통 상한을 보존한다.

새 시작에서는 원래 편성 인력 1,000명을 500명씩 두 부대로 나눠 선택·추가 선택을 연습할 수 있다. 공군 8대의 인력 800명도 기존 예산에서 이동한다. 육군 기지는 수도의 공군 기지와 겹치지 않도록 본인 육지의 3~5타일 인근에 배치하며, 작은 지역에서는 가까운 유효 타일로 줄인다. 모든 세력에 같은 시작 인구·자금·편성 예산을 적용한다. 공군·육군 기지 외에 Port를 복제하거나 인구를 추가하지 않는다.

부대가 공격·수송으로 이전된 병력은 native attack/transport 상태에서 한 번만 계산한다. 대기 중 육군 생산은 committed 인력에 포함한다. 취소된 신규 동원은 원래 세력의 가용 인력으로 돌아가고, 예비 육군 조립은 예비 병력으로 돌아간다. 점령자가 미완성 생산을 무료로 받지 않는다. native 전투 후 raw 병력의 1명 미만 잔량은 예비 풀에 보존하고 정수 인력 장부의 뷰에서만 내림한다.

해군·공군 생산의 예비 육군 출처도 `job.source`에 저장한다. 생산 취소·기지 점령 시 신규 가용 동원은 가용 풀에, 육군에서 재훈련한 승조원·조종사는 원래 육군 예비 풀에 돌아간다. 생산 전에 검증 실패하면 금·인력·예비 풀 모두 변하지 않으며, 이미 지불한 생산 취소 비용은 무료로 환불하지 않는다. 대기 중 스냅샷 복원에서 같은 출처로 한 번만 반환하는 것을 검사했다.

## 병력 곡선 측정

측정은 Node 24.15.0/Windows에서 실제 기준 checkout의 `Config`, `PlayerExecution`, `Setup`을 각각 불러 실행했다. fixture는 plains의 통행 가능한 육지 전체를 소유한 인간 한 명, 전투·AI·부대 생산 없음, raw 예비 170,000 = 17,000명, 현대 편성 1,000명과 공군 인력 800명, 인구 1,000,000명, 자금 400,000이다. `PlayerExecution`을 1,200 tick 실행한다. 속도·렌더 FPS·선택 키가 개입하지 않는다.

원본의 실제 지형 수용량은 602,377.286 raw이다. 원본 곡선 자체의 비교에는 수용량만 현대 예비 수용량 982,000 raw로 정규화한 별도 실행을 사용했다. 원본의 자연 수용량 실행과 정규화 실행을 구분한다. 현대 전체 동원 상한은 인구의 10%이며 해군·공군 인력을 차감하고, 편성 중·출정 중 육군도 동일한 총 육군 상한에 포함한다.

정규화한 원본과 수정본의 가장 큰 표본 차이는 30초의 13.1명(약 0.0195%)이다. 원본은 raw 증가를 tick마다 반올림하고, 수정본은 같은 식을 명시적으로 양자화한 후 1/1,000명 잔량을 저장하여 실제 정수 인력을 이전한다. 같은 곡선을 무조건 배수로 늘린 결과가 아니다.

모든 표본에서 `민간 + 가용 + 육군 + 해군 + 공군 = 전체 생존 인구 = 1,000,000`, 사망 인구는 0이었다. 수정본의 민간 인력은 970,000→887,608명으로 줄었으며, 훈련 비용을 실제 지불했다. 120초에 1명/tick로 느려지는 것은 99,826명으로 동원 상한 100,000명에 접근했기 때문이다. 시작부터 고정 2명/tick로 느리던 결함과 다르다.

원본 곡선의 수용량은 현재 병력과 함께 매 tick 재평가한다. 핵 보충 페널티, 자금·인력 부족, 동원 상한은 복구한 곡선에도 적용한다. 민간인 훈련은 필요한 보충량과 가용 인력의 완충량을 따라가되 실제 민간인·가용 수용량·금 예산으로 제한한다. 잔량은 simulation과 스냅샷에 저장한다.

위 실험은 **병력·훈련만 분리한 비교**여서 항공기의 주기 유지비를 실행하지 않는다. 실제 경기에서는 이 예시의 항공기 8대 유지비가 별도로 100 tick마다 200금 지출된다. 전투 손실·산업 투자·핵 페널티가 있는 실제 경기의 경제 예측으로 이 표를 사용하지 않는다.

## 저장·리플레이와 검사

Game snapshot record는 **3**으로 올렸다. record 2 migration은 이전 현대 state 2의 `legacy-fixed` 증가식, 공군 기지 기본 종류, 빈 생산·완료 기록, 잔량 기본값을 채운다. 이전 게임의 국경·AI 배정·인구·자금·시설·부대를 다시 생성하지 않는다. 원래 record 1→2 migration도 유지한다. `ModernPortTrainingExecution`은 2로 올려 이전 기록에는 건조 중 군함 ID를 null로 채운다. 10Hz 위치·경로 출력 캐시는 파생 표시 상태여서 저장하지 않고 복원 시 비운다.

`tests/ModernRepairCore.test.ts`는 실제 지상 공격·점령 위치·지연 철수와 인력 회계, 건설·생산의 정확한 완료 tick, 비용/인력 예약, 생산 중 용량, 점령 시 취소, 피해/수리 연기, native Port/Warship 중복 방지, 정규화 성장, 핵 보충 감소, 동원 상한 이후 예비 편성, v2 raw snapshot migration과 같은 빌드의 성장·생산·철수 중 복원을 확인한다. `ModernForces`, `ModernAI`, `ModernSystems`, `ModernWorld`, modern replay codec 회귀를 함께 실행한다.

```sh
npx vitest run tests/ModernRepairCore.test.ts tests/ModernForces.test.ts tests/ModernAI.test.ts tests/ModernSystems.test.ts tests/ModernWorld.test.ts tests/client/replay/codec/ModernSystems.test.ts --maxWorkers=4 --testTimeout=20000
```

35개 공군 편대의 명령 분할 검사는 **명시적인 custom roster 한도 64**를 사용하는 fixture이다. 기본 게임의 편성 한도 24를 늘리지 않는다. 실제 기지 2개의 총 수용량 48, 동일 N0와 자금, 유료 생산과 완료 tick을 지키며 35개 편대 생성 후 32/3개의 두 Intent와 소유권 거절, 모든 경로의 저장·복원을 검사한다. 기본 게임에서 공군 35개 편대를 제공한다는 증거로 쓰지 않는다.

core 검사는 UI 발견 가능성·실제 마우스 좌표·튜토리얼 완료를 대신하지 않는다. 정상 메뉴의 새 빌드 브라우저 플레이, 원본 스타일 비교, 전체 키 설정과 성능 결과는 최종 통합 검증 문서에 별도로 기록한다.

위 여섯 파일의 이번 수정본 검사는 **100개 통과 / 실패 0**(24.62초), 전체 TypeScript 검사와 core 변경 파일의 ESLint는 exit 0이었다. 원래 커밋의 과거 통과 개수와 구분한다. 실행 로그는 작업 공간 `outputs/repair-core-tests-retrain-final.log`, `repair-core-tsc-retrain.log`, `repair-core-lint-retrain.log`이다. 브라우저 실습 완료와 AI 성능 목표 달성 여부는 이 결과에 포함하지 않는다.

동일 조건 성능은 [이전 9회·최종 4회 실측과 미달 목표](benchmarks/repair/perf/REPORT.md)에 기록했다. core 회귀 통과와 tick 성능 목표 달성을 구분한다. 이전 mixed p95 증가는 +11.08% / +20.60%로 두 번째가 20% 목표를 넘었고, low는 +28.18%다. 최종 source의 추가 paired 두 mixed는 +8.60% / +9.40%였지만 이전 미달과 서로 다른 규모의 v1/v2 전체 비용 목표 미달을 유지한다. AI 수를 줄이거나 판단을 끈 결과가 아니다.

이번 후보의 전체 회귀 첫 실행은 621파일 중 613 통과·8 실패, 검사 7,732 통과·68 실패·1 skip(534.22초)이었다. 6개 POSIX 배포 셸 suite의 67 실패는 이 Windows 환경의 `sh` 부재/`bash -c` 실행과 도구 의존에 해당한다. 나머지는 전체 조작표의 `education.description` 번역 누락 1건과, 새 Modal import에 필요한 `query`가 기존 ReplayPanel의 제한적인 Lit mock에 없는 suite 로딩 실패였다. core/native/기존 snapshot·save·replay codec의 실패는 없었다.

번역의 실제 누락을 추가한 뒤 드러난 미사용 문구도 정리했다. 새 `input_actions` registry와 도움말로 대체된 키는 `resources/education/obsolete-repair-keys.json`의 버전 1 목록으로 관리한다. 초기 목록은 101개였으나, 최종 터치 조작의 실제 확정 버튼이 `modern_v2.confirm`을 사용하므로 이 키를 복원하여 **최종 삭제 목록은 100개**다. `mergeModernTranslations.ts`는 EN/KO 원문과 생성 파일에서 이 정확한 목록만 제거하며 입력 action은 삭제하지 않는다. 현대 실습 힌트 8개도 실제 안내에 연결하여 보존한다. 번역 검사 기준을 완화하거나 사용되지 않는 가짜 참조를 추가하지 않았다. 초기 정리 시 원문·생성 8개 파일은 재생성 후 SHA-256이 모두 같았으며, 이후 추가한 실제 안내·터치 문구는 최종 검사의 대상으로 구분한다.

ReplayPanel mock에 `query` export만 보완하고 기존 세 동작 검사를 유지했다. 이 두 실패 suite의 후속 검사는 6개 전부 통과(2.62초), 변경 generator·mock ESLint는 exit 0이다. 로그는 `outputs/repair-full-followup-translations-replaypanel-2.log`와 `repair-full-followup-translations-replaypanel-lint.log`다. POSIX 6개를 제외한 전체 재실행과 후속 input/UI 변경의 최종 결과는 통합 보고서에서 구분한다.

최종 입력·터치 변경을 포함한 동결 후보 `64a4a035a0e4`의 전체 portable 재실행은 **615파일·7,736검사 통과·1 skip, 실패 0**(510.01초), 별도 서버 단계는 81파일·904검사 전부 통과(50.69초), whole lint는 exit 0이었다. 실행 전후 관련 source 1,590파일의 SHA가 같았다. 정확한 제외 범위·명령·이전 실패와의 구분은 [최종 검사 기록](RepairAcceptanceChecks.md)에 있다. 이것은 최종 후보의 성능 재측정이나 실제 교육 완주 증거가 아니다.

이후 실제 태블릿 경기에서 항구 건설 미리보기의 불일치를 추가로 확인했다. 소유 해안 `573713`은 UI가 유효하다고 표시했지만 native `Port.canBuild`는 기존 시설 간격 때문에 false였고, 요청 `627705`의 native 유효 위치는 `631703`이었다. `ModernCommandPanel`의 placement를 기존 Worker `buildables(tile, [Port])`에 연결하여 실제 가격과 조정 위치를 표시한다. 아직 응답이 없거나 false인 경우 명령을 보내지 않는다. Confirm 직전에 재검증하고 위치·가격이 달라졌으면 갱신된 미리보기에서 다시 확인하게 한다. 이전 목적지·취소·종료 후 응답을 폐기하며 기존 Port 아이콘의 반투명 미리보기만 추가했다.

core의 `navalBase`는 기존 Port 검색 한 번과 원래 건설을 유지하고, 비활성·금 부족·유효 부지 없음의 거절 이유를 구분한다. 실제 City가 native 15타일 간격을 막는 회귀에서 명령 거절 후 금·인구·상태가 그대로임을 확인했다. 다른 회귀에서는 native가 선택한 해안에 같은 가격으로 Port 한 개가 건설되고 50 tick의 실제 완료 시점까지 공사 중임을 확인했다. 후속 core·패널·native Port·캐시 **5파일 85검사 통과**(10.04초), TypeScript와 변경 파일 lint는 exit 0이었다. 로그는 `outputs/repair-native-port-validation-tests.log`, `repair-native-port-validation-tsc.log`, `repair-native-port-validation-lint.log`다. 이는 위 615파일 전체 실행 이후의 수정이며, 새 빌드의 태블릿 재검증과 구분한다.

이 Port 수정까지 포함한 마지막 portable 전체 실행은 **615파일·7,742검사 통과·1 skip, 실패 0**(504.81초, exit 0), 별도 서버 단계는 81파일·904검사 통과(50.43초), whole lint exit 0이었다. 실행 전후 1,590파일 대조에서 core/tests/교육·언어 자료/scripts 변경은 없었고 `PlayPage.ts`의 모바일 저장 버튼 위치만 후속 수정되었다. 그 UI 변경의 검사는 별도 범위로 기록한다. 새 로그는 `repair-acceptance-final-full/server/lint.log`이며 [검증 시점과 제외 범위](RepairAcceptanceChecks.md)를 따른다. 병력 곡선 실측, 성능 실측, 브라우저 교육 완료는 각각의 원자료로 판단한다.
